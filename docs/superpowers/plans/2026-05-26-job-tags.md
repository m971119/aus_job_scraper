# Plan: Job Tags Feature

## Requirements

- Global tags shared across all jobs (many-to-many)
- Users can type to create new tags or select existing ones
- Tags are managed on the job detail page
- Four default tags pre-seeded: Interested, Laravel, Python, AI
- "Interested" badge shown on the main job listing beside the repost badge
- Main listing page can be filtered by tag

---

## Success Criteria

- [ ] Migration creates `tag` and `job_tag` tables and seeds default tags
- [ ] `GET /api/tags` returns all tags
- [ ] `POST /api/tags` creates a new tag (name unique, case-insensitive)
- [ ] `POST /api/jobs/{id}/tags/{tag_id}` applies a tag to a job
- [ ] `DELETE /api/jobs/{id}/tags/{tag_id}` removes a tag from a job
- [ ] `GET /api/jobs` accepts optional `?tag=<name>` filter and returns only matching jobs
- [ ] Job detail page shows current tags and a type-to-create-or-select input
- [ ] Removing a tag from a job does not delete the global tag
- [ ] "Interested" badge appears on job listing rows when that tag is applied
- [ ] Default tags survive a fresh DB creation (seeded in migration)

---

## Database

### New tables

**`tag`**
| column | type | notes |
|---|---|---|
| `id` | INTEGER PK | |
| `name` | TEXT UNIQUE | case-insensitive unique enforced at API layer |

**`job_tag`** (association)
| column | type | notes |
|---|---|---|
| `job_id` | INTEGER FK → job.id | |
| `tag_id` | INTEGER FK → tag.id | |
| composite PK on (job_id, tag_id) | | prevents duplicates |

### Migration file
`backend/alembic/versions/0003_add_tags.py`
- Creates `tag` table
- Creates `job_tag` table with composite PK and FK constraints
- Seeds four default tags: Interested, Laravel, Python, AI
- `downgrade`: drops both tables

### Model changes (`backend/models.py`)
- Add `Tag(SQLModel, table=True)` with `id`, `name`
- Add `JobTag(SQLModel, table=True)` with `job_id`, `tag_id` (composite PK)
- No SQLModel relationship links needed — queries join manually to keep it simple

---

## Backend

### Schema changes (`backend/schemas.py`)
- `TagOut`: `id: int`, `name: str`
- `JobOut`: add `tags: list[TagOut] = []`

### New route file `backend/routes/tags.py`
| method | path | description |
|---|---|---|
| GET | `/api/tags` | list all tags |
| POST | `/api/tags` | create tag (body: `{name}`, reject duplicate) |
| POST | `/api/jobs/{id}/tags/{tag_id}` | apply tag to job (idempotent) |
| DELETE | `/api/jobs/{id}/tags/{tag_id}` | remove tag from job |

### Changes to `backend/routes/jobs.py`
- `GET /api/jobs`: accept optional `tag` query param; join `job_tag` + `tag` to filter
- `GET /api/jobs/{id}`: join to include `tags: list[TagOut]` in the response

---

## Frontend

### New component `frontend/components/TagManager.tsx`
- Shown on job detail page
- Displays current tags as removable chips
- Combobox input: filters existing tags as user types, shows "Create tag" option when no match
- On select or create: calls POST to apply tag
- On chip remove: calls DELETE to remove tag

### Changes to `frontend/components/JobCard.tsx` (or equivalent listing row)
- After the repost badge, check if `tags` includes `"Interested"`
- If so, render an "Interested" badge (accent yellow `#ecad0a`)

### Changes to `frontend/app/page.tsx` or `JobList`
- Add tag filter UI (dropdown or tag chip selector) above the job list
- Pass selected tag as `?tag=<name>` query param to `GET /api/jobs`

### Changes to job detail page/component
- Render `<TagManager jobId={id} initialTags={job.tags} />`

## Unit Tests

All tests live in `backend/tests/` and use the existing `TestClient` + in-memory SQLite pattern from `test_api.py`. The `clean_db` autouse fixture wipes and recreates all tables before each test — no mocking.

### `test_tags.py` — tag CRUD

| test | what it proves |
|---|---|
| `test_list_tags_empty` | `GET /api/tags` returns `[]` on fresh DB |
| `test_list_tags_returns_defaults` | after seeding, default tags (Interested, Laravel, Python, AI) are present |
| `test_create_tag` | `POST /api/tags` with `{"name": "Django"}` returns 201 with `id` + `name` |
| `test_create_tag_duplicate_rejected` | second `POST` with same name (any case) returns 409 |
| `test_create_tag_case_insensitive_duplicate` | `"python"` rejected when `"Python"` already exists |
| `test_create_tag_empty_name_rejected` | `{"name": ""}` returns 422 |

### `test_job_tags.py` — applying / removing tags

| test | what it proves |
|---|---|
| `test_apply_tag_to_job` | `POST /api/jobs/{id}/tags/{tag_id}` returns 200; tag appears in `GET /api/jobs/{id}` |
| `test_apply_tag_idempotent` | applying the same tag twice returns 200 both times, tag appears once |
| `test_apply_tag_wrong_job_returns_404` | non-existent job id returns 404 |
| `test_apply_tag_wrong_tag_returns_404` | non-existent tag id returns 404 |
| `test_remove_tag_from_job` | `DELETE /api/jobs/{id}/tags/{tag_id}` returns 200; tag absent from `GET /api/jobs/{id}` |
| `test_remove_tag_does_not_delete_global_tag` | after DELETE, `GET /api/tags` still includes the tag |
| `test_remove_tag_not_applied_returns_404` | removing a tag not on the job returns 404 |
| `test_job_detail_includes_tags` | `GET /api/jobs/{id}` response contains `tags` array with correct names |
| `test_job_detail_tags_empty_by_default` | freshly created job has `tags: []` |

### `test_tag_filter.py` — filtering jobs by tag

| test | what it proves |
|---|---|
| `test_filter_by_tag_returns_matching_jobs` | `GET /api/jobs?tag=Interested` returns only jobs with that tag |
| `test_filter_by_tag_excludes_untagged_jobs` | jobs without the tag are absent from results |
| `test_filter_by_tag_case_insensitive` | `?tag=interested` matches jobs tagged `"Interested"` |
| `test_filter_by_unknown_tag_returns_empty` | `?tag=nonexistent` returns empty list, not 404 |
| `test_filter_by_tag_combined_with_keyword` | `?tag=Python&keyword=senior` filters correctly on both dimensions |
